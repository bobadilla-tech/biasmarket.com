## Context

`collections` is the only feature on the new pattern
(`apiClient.collections.findAll(storeId)`, generated by Orval from
`apps/api/openapi.json`, no `api/` wrapper folder). Every other feature — 15
`features/<name>/api/` folders, mapping to 24 of `apps/api`'s 25 OpenAPI tags —
is still on the old `apiFetch` + zod pattern (`lib/api.ts`). This doc scopes
migrating the rest, module by module.

**The real work is not codegen config — it's response DTOs.** Every controller
except `collections` still returns whatever its Prisma-backed service resolves
to: no `Promise<T>` return types, no response DTO classes, no `@ApiProperty`.
`@nestjs/swagger` emits an anonymous `{ [key: string]: unknown }` placeholder
for these, which (a) isn't a real type and (b) — confirmed during the
`collections` rollout — collides by name with every other untyped controller's
same-named operations (`findAll`, `create`, ...) in Orval's shared
`api.schemas.ts` the moment more than one such tag is generated at once. **A tag
must not be added to `packages/types/orval.config.ts`'s `filters.tags` until its
controller has real response DTOs** — giving a controller real response DTOs is
most of the effort per module, same as the original plan doc said before any of
this was built.

## Still-outstanding gate from the original plan (not superseded by the Orval switch)

The original plan's Phase 1 required proving the response-DTO pattern on a
money-bearing module and a multipart-upload module before wider rollout —
`collections` only incidentally touched money (via a nested `product.price`
join) and never touched uploads. **That gate is still open.** `products` hits
both (money fields directly on the DTO, `productsControllerUploadImage`

- `UploadVariantImage`) — migrate it early, not last, so the gate closes before
  most of the remaining ~23 modules are attempted. See
  `docs/core/security-payments.md` and root `CLAUDE.md`'s Decimal-never-Float
  rule; get a second pair of eyes (or extra care) on `products`' and `orders`'
  response DTOs specifically.

## Per-module recipe

Repeat for each tag. Steps 1–4 are backend (`apps/api`); 5–9 are frontend
(`packages/types` / `apps/web`).

1. **Read the service.** Find the controller's methods
   (`apps/api/src/modules/<module>/*.controller.ts`) and read what its service
   actually returns — don't guess the shape from the Prisma schema alone
   (joins/includes reshape it).
2. **Write response DTO classes** (`dto/<name>-response.dto.ts`), matching
   `collections/dto/collection-response.dto.ts`'s conventions exactly:
   - Money/`Decimal` and `Date` fields are typed `string` on the DTO (never
     `Prisma.Decimal`/`Date`/a Prisma-generated enum type — doing so breaks the
     `PluginMetadataGenerator` script, see the first plan doc's Phase 0/1
     execution notes) — the controller method does the
     `Decimal`→`string`/`Date`→ISO-string mapping before returning, matching
     `CollectionsController.findAll`'s pattern.
   - Give every controller method an explicit `Promise<...Dto>` /
     `Promise<...Dto[]>` return type so the plugin can infer the OpenAPI schema.
   - Multipart upload endpoints (`UploadedFile`/`FileInterceptor`) don't fit a
     JSON request-body schema — leave the _request_ side alone
     (`@ApiConsumes('multipart/form-data')` if not already present) and keep the
     _frontend_ upload call on plain `fetch`/`FormData` (see step 7); only the
     JSON response side needs a DTO.
   - Recheck the metadata-generator self-poisoning failure mode (Phase 0/1
     notes): if `apps/api/src/metadata.ts` stops updating silently, delete it
     and rerun.
3. **Regenerate the spec**: `pnpm --filter api generate:openapi`. Manually diff
   the new `openapi.json` paths for this module against the service code (the
   Phase 1 stop-and-verify checkpoint) — this only catches drift once, at
   authoring time.
4. **Add an e2e contract test**, one per migrated module, same shape as
   `apps/api/test/collections.e2e-spec.ts`: hits the real endpoint via
   `supertest` against a real `AppModule`, validates the live response against
   the corresponding schema in the generated `openapi.json`. Note the e2e
   harness doesn't run `main.ts`'s `bootstrap()` — no global `/api` prefix, hit
   routes at their bare path (`/stores/...`), unlike the real app.
5. **Add the tag** to `packages/types/orval.config.ts`'s `input.filters.tags`
   array (only after step 2 is real, per the gate above). Regenerate:
   `pnpm --filter @biasmarket/types generate`. Add the new tag's namespace
   export to `packages/types/index.ts`
   (`export * as <tag> from "./generated/<tag>/<tag>.js";`) and a matching key
   to `apps/web/lib/api-client.ts`'s `apiClient` object.
6. **Check the generated method names** for reserved-word collisions (`delete` →
   Orval falls back to `_delete`; the `collections` config already remaps that
   one to `remove` — extend that same `operationName` function, don't add a
   second one) and skim for any other awkward names before wiring call sites to
   them.
7. **Rewrite `features/<name>/`**: delete (or shrink) the `api/*.ts` file;
   `queries/`/`mutations/` call `apiClient.<tag>.*` directly, matching
   `features/collections/queries/use-collections.ts` /
   `mutations/use-create-collection.ts`. Move any real per-call transformation
   (e.g. `collections`' empty-string→`undefined` description normalization) into
   the mutation hook itself, not a surviving wrapper function. Pass
   `{ fallbackErrorMessage }` as the trailing options arg wherever the old code
   passed a fallback message string. **Multipart upload calls are the one
   exception** — they don't route through the generated client at all; keep them
   on `apiFetch`/raw `fetch` + `FormData` exactly as `lib/api.ts` does today,
   calling the feature's remaining upload-specific function directly (this
   mirrors the original plan doc's explicit multipart carve-out).
8. **Response-shape zod**: drop it for plain pass-through reads once a type
   comes from the generated client (`features/<name>/schemas/*.ts` becomes type
   aliases onto the generated `*ResponseDto` types, same as
   `collection.schema.ts`); keep zod for request/form validation and any real
   client-side derived parsing (money-string→number, date formatting, etc.) —
   this split is already documented in `apps/web/AGENTS.md`, apply it
   per-module, not as a blanket change.
9. **Verify per module**:
   `pnpm --filter api test && pnpm --filter api
   test:e2e`,
   `pnpm --filter @biasmarket/types typecheck`,
   `pnpm --filter
   web typecheck && pnpm --filter web test && pnpm --filter web build`.
   For at least the first 2–3 modules migrated in a session, also smoke-test
   against the real running `apps/api` dev server the way the `collections`
   session did — a plain Node script (not a browser; `chromium-cli` drives the
   user's real, already-open Chrome on this machine, don't script it) importing
   `packages/types`'s built `dist/index.js`, exercising the module's real
   endpoints end to end. Once the recipe feels mechanical across a few modules,
   later ones in the same session can lean on typecheck/test/build alone.

After each module: update `apps/web/AGENTS.md`'s migration roadmap section (mark
it done, one line, matching the existing `~~done~~` convention) and append to
this doc's own execution notes once the whole rollout — or a meaningfully-sized
batch of it — lands, per `docs/plans/README.md`'s convention.

## Known blocker: fix or route around the `CustomerAuth` spec bug first

`CustomerAuthController_changePassword` and `_logout` are missing their `slug`
path parameter in the emitted spec (see the follow-up doc's execution notes) —
Orval's validator hard-fails the _entire_ generation over this, repo-wide, not
just for `CustomerAuth`. Right now this is routed around with
`input.unsafeDisableValidation: true` +excluding the whole `CustomerAuth` tag.
Before migrating `features/customer-auth`, either:

- fix the underlying `apps/api` Swagger annotation gap (add the missing
  `@Param`/`@ApiParam` for `slug` on those two methods — a small, isolated fix,
  unrelated to DTOs), or
- confirm Orval still has no per-operation filter (only tag/schema granularity
  as of `orval@8.23.0`) and keep excluding just those two operations some other
  way. Don't leave `unsafeDisableValidation: true` load-bearing forever without
  revisiting it — it was accepted for `collections` because the bug was in an
  unrelated, not-yet-migrated tag; once `CustomerAuth` itself needs migrating,
  the bug needs an actual fix, not a wider validation bypass.

## Non-goals

- **Not doing all 24 tags in one PR/session.** Batch-by-batch (or
  feature-by-feature, whichever a session has room for), same incremental
  posture as every prior phase of this effort.
- **Not applying the DDD-lite `domain/application/infrastructure` layering** to
  flat CRUD modules while doing this — per root `CLAUDE.md`, that layering is
  reserved for `orders`/`payments`-shaped work already in progress, don't bolt
  it onto `categories`/`contact` as a side effect of a DTO pass.
- **Not adopting TanStack Query hook generation** — already decided against in
  the follow-up doc's execution notes; don't relitigate per module.
- **Not touching `packages/db`, auth internals, or deployment config** as part
  of this — response DTOs and frontend consumption only, except the one small
  `CustomerAuth` spec-annotation fix called out above.

## Batch 1 execution notes (2026-08-05)

`Products` migrated end to end, closing the still-outstanding money/upload gate
from the original plan. Matches the per-module recipe exactly; notes below are
what diverged from a mechanical read of it.

- **Response DTOs**: `apps/api/src/modules/products/dto/product-response.dto.ts`
  — `ProductResponseDto` (base row), `ProductWithVariantsResponseDto` (extends
  it, `create()`'s shape — product + variants, no category join), and
  `ProductDetailResponseDto` (extends that, `findAllForStore()`/`findOne()`'s
  shape — adds the category join plus `soldUnits`/`availableStock`), plus
  `VariantResponseDto` and a nested `CategoryInProductResponseDto`/
  `ProductCategoryResponseDto` pair for the category join row (mirrors
  collections' `ProductInCollectionResponseDto` nesting pattern). `price`/
  `priceOverride` are `string`; `status` is a literal `"DRAFT" | "PUBLISHED"`
  union, not the Prisma-generated enum — same conventions as `collections`.
  `VariantResponseDto.attributes` needed
  `@ApiProperty({ type: "object", additionalProperties: { type: "string" } })`,
  not the bare `{ type: "object" }` collections' comment implies is enough —
  `@nestjs/swagger`'s `SchemaObjectMetadata` type requires
  `additionalProperties` on an object-typed property or `tsc` rejects the
  decorator call outright (a real, not hypothetical, type error, not a schema
  soundness prompt).
- **Controller mapping**: `ProductsController` gained two local, non-exported
  helpers (`toProductDto`/`toVariantDto`) instead of inlining the
  `Decimal`→`string`/`Date`→ISO mapping in all 9 non-upload methods separately
  (`collections` only had one method to map, so this pattern didn't come up
  there). Their parameter types (`ProductRow`/`VariantRow`) are structural —
  `price`/`priceOverride` typed `{ toString(): string }` rather than
  `Prisma.Decimal` — to stay out of the `PluginMetadataGenerator` failure mode
  Phase 0/1's notes describe, without needing per-method duplication.
- **A real, pre-existing type hole in `ProductsService.findAllForStore` surfaced
  by adding an explicit controller return type**: its length-0 early return
  (`if (products.length === 0) return products;`) returned the bare Prisma
  include-shape (no `soldUnits`/`availableStock`), while the populated path
  added those two fields — an unannotated method, so TypeScript silently
  accepted the inconsistent union return type. Once `ProductsController.findAll`
  declared `Promise<ProductDetailResponseDto[]>` and tried to read
  `.soldUnits`/`.availableStock` off the mapped array, `tsc` correctly refused
  (the union's empty-array branch doesn't have those fields). Fixed with a
  one-line change to the service (`return products;` → `return [];` —
  behaviorally identical, since `products` is already `[]` on that branch)
  rather than touching the controller mapping. Read this as: giving a controller
  an honest return type is itself a real correctness check on the service
  underneath it, not just plumbing for codegen.
- **Multipart upload endpoints** (`uploadImage`, `uploadVariantImage`) got
  `@ApiConsumes("multipart/form-data")` (missing before) and a real
  `Promise<ProductResponseDto>`/`Promise<VariantResponseDto>` return type, same
  DTO-mapping treatment as every other method — but per the recipe's carve-out,
  `apps/web` never calls Orval's generated functions for these two operations
  (Orval does generate `uploadImage`/`uploadVariantImage` functions from the
  spec — unlike hey-api, it doesn't need an explicit exclusion — they're just
  unused dead code from `apps/web`'s side).
  `features/products/api/products.api.ts` was kept, shrunk from ~10 methods down
  to just these two (`uploadMultipart` + the two exported functions), exactly
  the recipe's stated exception.
- **`orval.config.ts`**: `filters.tags` extended to
  `["Collections", "Products"]`. No new reserved-word remap needed — `Products`'
  only delete-shaped method is named `softDelete`, not `delete`, so the existing
  `delete` → `remove` override in `operationName` never triggers here. Every
  generated method name came out clean on the first try (`create`, `findAll`,
  `findOne`, `update`, `publish`, `softDelete`, `addVariant`, `listVariants`,
  `updateVariant`, `deleteVariant`, `uploadImage`, `uploadVariantImage`).
- **e2e contract test**: `apps/api/test/products.e2e-spec.ts`, same
  self-contained shape as `collections.e2e-spec.ts` (no shared test helper
  extracted — each e2e spec duplicates its own `assertMatchesSchema`/
  `resolveSchema`, matching the one prior example). Exercises create → list →
  variant price-override update → real multipart image upload (a 1×1 PNG buffer,
  not a mocked file), asserting both schema-shape and that
  `price`/`priceOverride`/`deletedAt` are real strings at runtime, not just
  typed as strings. `updateVariant`'s stock-alert side effect
  (`NotificationsService.syncStockAlerts`) writes a `Notification` row keyed by
  `storeId`, which `collections.e2e-spec.ts`'s `afterAll` cleanup order didn't
  need to handle — `products.e2e-spec.ts`'s does
  (`prisma.notification.deleteMany` before `store.deleteMany`, or the store
  delete fails on the `Notification_storeId_fkey` constraint).
- **Local-infra gotchas, same class as Phase 0/1's notes, worth re-confirming
  rather than re-discovering**: the multipart e2e test needs a real
  S3-compatible endpoint reachable at `S3_ENDPOINT` — `minio` (the hostname
  `infra/docker/docker-compose.dev.yml` uses) only resolves inside that compose
  network; from a bare `pnpm exec vitest` on the host, use
  `S3_ENDPOINT=http://localhost:9000` against a standalone
  `docker compose -f infra/docker/docker-compose.dev.yml up -d minio
  minio-init`
  instead of the full dev stack. `RESEND_API_KEY` and friends aren't loaded
  automatically in the e2e harness either (only `main.ts` imports
  `dotenv/config`, and e2e tests boot `AppModule` directly) — export
  `apps/api/.env`'s vars into the shell first
  (`set -a && source .env && set +a`).
- **Verification performed**: `pnpm --filter api test` (283 tests, all green —
  required updating `products.controller.spec.ts`'s mocks to return realistic
  row shapes instead of `undefined`, since the controller methods are now
  `async` and dereference fields like `.price`/`.variants` on the service's
  resolved value before returning — the old delegate-only tests didn't await the
  call or care about the return value at all), the new `products.e2e-spec.ts`
  plus the existing `collections.e2e-spec.ts`/ `app.e2e-spec.ts` together (they
  don't collide with each other; running the dedicated
  `customer-auth-rate-limit.e2e-spec.ts` in the same process does 429 the
  others' sign-in calls — a pre-existing test-isolation gap between that spec
  and every other e2e spec, unrelated to this change),
  `pnpm --filter @biasmarket/types typecheck`,
  `pnpm --filter web
  typecheck/test/build` (184 tests across 59 files, clean
  build), and a standalone Node script (same shape as the collections session's
  verification, per the recipe's step 9) importing
  `packages/types/dist/index.js` against the real running `apps/api` dev server
  — signup → verify → sign-in → create-store →
  `products.create/findAll/updateVariant/publish/softDelete/findOne`, confirming
  `price`/`priceOverride`/`deletedAt` are real strings at runtime and that a 404
  on a soft-deleted product throws through the mutator as expected. Not
  browser-verified (per the collections session's precedent, scripting the
  user's real Chrome via `chromium-cli` was declined as inappropriate) — a
  manual click-through of the products dashboard page is still worth doing
  before this ships.
- **Frontend**: `features/products/schemas/{product,variant}.schema.ts` dropped
  their zod response schemas for plain type aliases onto
  `ProductDetailResponseDto`/`VariantResponseDto` (their corresponding
  `.test.ts` files, which only tested the now-deleted `.parse()` calls, were
  deleted, same as `collections.api.ts`'s test was); `VariantDraft`/
  `OptionTypeDraft` (local UI-state types, not response shapes) stayed.
  `queries/`/`mutations/` now call `apiClient.products.*` directly, matching
  `collections`' pattern — `use-update-product.ts`'s variant-diffing logic is
  otherwise unchanged, including the `Promise.allSettled` upsert-then-delete
  behavior documented on the hook already; its swallow-delete-errors behavior
  (`productsApi.deleteVariant(...).catch(() => undefined)` in the old code)
  moved to the call site
  (`apiClient.products.deleteVariant(...)
  .catch(() => undefined)`) per the
  recipe's "move real per-call transformations into the hook" instruction.
  `use-update-product.test.tsx` was rewritten to mock `@/lib/api-client`'s
  `apiClient.products.*` instead of `@/lib/api`'s `apiFetch` — no prior example
  of mocking the generated-client shape existed in this repo (`collections` has
  no mutation tests at all), so this is the first one. `features/products`
  (Categories tag) was deliberately left untouched — it's Batch 2, a separate

## Batch 2 execution notes (2026-08-05)

`Categories`, `Notifications`, `Contact`, `Suggestions`, `StoreSections` all
migrated end to end, matching the per-module recipe. All five are small CRUD
modules as expected — no money fields, no uploads — but two real gotchas came up
that the "small, low-risk" framing didn't anticipate:

- **`Notifications.findAll` needed real `@ApiQuery` decorators, a first for this
  repo.** The existing controller read `archived`/`read` off `@Query()` with no
  Swagger annotation at all, so `@nestjs/swagger` emitted no query-parameter
  schema and Orval's generated `findAll` silently dropped both filters — not a
  crash, just a client that compiles fine and quietly ignores the
  archived/unread tab filtering the dashboard depends on. Fixed with
  `@ApiQuery({ name: "archived", required: false, type: String })` (and the same
  for `read`) directly on the controller method — no request DTO class needed
  since the params were already hand-parsed strings. Orval then generates a
  `FindAllParams` type and a `params?` positional argument ahead of `options`.
  Watch for this on every future query-string endpoint migrated in later batches
  (there's no existing `@ApiQuery` usage anywhere else in the repo to copy from,
  so this is now the reference example).
- **`FindAllParams` lives in the single shared `api.schemas.ts`, unnamespaced by
  tag** — same root cause as the `FindAll200Item` collision Batch 1's gate was
  supposed to catch, just not yet triggered because `Notifications` is the only
  tag with a query-param'd `findAll` so far. The next module that adds a
  query-string parameter to a method also named `findAll` (or any other
  already-used method name) will collide the same way the untyped-placeholder
  responses did before the "only add a tag once its DTOs are real" rule. No fix
  needed today — just noting it as a rule to re-derive when it actually happens,
  the same way the original collision was handled.
- **Running more than ~3 e2e spec files in parallel trips better-auth's built-in
  sign-in/sign-up rate limiter repo-wide, not just via the dedicated
  `customer-auth-rate-limit.e2e-spec.ts`.** Adding 5 new e2e specs (each doing
  its own signup+verify+signin in `beforeAll`) brought the concurrently-running
  total to 8 files; Vitest's default file-level parallelism fired all their
  signups within the same ~10s window, and better-auth's default rule (3
  sign-in/sign-up requests per 10s, see `auth.config.ts`) started rejecting
  later ones with `403`, not `429` (easy to misread as an auth bug instead of a
  rate limit). Fixed at the config level, not per-invocation:
  `vitest.config.e2e.ts` now sets `fileParallelism: false`, so
  `pnpm --filter api test:e2e` runs every spec file sequentially by default — no
  flag to remember, no risk of someone reintroducing the flake by running the
  bare command. This will keep mattering more as more modules gain e2e specs.
- **The e2e specs' own `assertMatchesSchema` test helper (duplicated per file,
  per the established convention) didn't handle `additionalProperties: true`** —
  needed for `Notifications.metadata`, `Suggestions.bodyParams`, and
  `StoreSections.content`, all untyped JSON fields. The helper's object-property
  loop rejected any key not explicitly listed in `properties`, which is correct
  for closed schemas but wrong for an open one. Fixed by checking
  `resolved.additionalProperties` before throwing on an undeclared key. Copy the
  fixed version (not the original `collections.e2e-spec.ts` one) into any future
  e2e spec that touches an open/untyped JSON response field.
- **`Contact` has no `storeId` at all** (`ContactInquiry` is explicitly
  platform-level, per the schema comment) and its admin-only endpoints
  (`findAll`, `markReviewed`) are `@Roles(["admin"])`-gated with no public
  "become admin" flow — the e2e spec and the `apps/web/features/admin` migration
  both seed `role: "admin"` directly via Prisma after a normal sign-up, since
  that's the only way to reach those endpoints outside production.
  `features/admin/api/inquiries.api.ts` was migrated in this batch too (not a
  separate tag — see the original plan doc's "already covered by earlier
  batches" list), calling the same generated `apiClient.contact.*` the public
  `features/contact` submit form uses.
- **A node-script smoke test against the real dev server needs an `Origin`
  header better-auth accepts, or every state-changing auth call 403s with
  `MISSING_OR_NULL_ORIGIN`** — `curl` without an `Origin` header worked (no
  browser-like default), but plain Node `fetch` calls from a script hit
  better-auth's origin check the same way a real disallowed cross-origin browser
  request would. Setting `Origin: http://localhost:3001` (matching `WEB_URL`) on
  every request fixed it. Worth remembering for any future session's smoke-test
  script — `apiFetch`/the generated client's mutator never need this in the real
