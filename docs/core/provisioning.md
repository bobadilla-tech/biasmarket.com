# Server provisioning

How the production VPS is created, and how a replacement is brought to the point
where the first blue/green deploy can run. Normal deploys are described in
[deploy.md](deploy.md) and [blue-green-migrations.md](blue-green-migrations.md);
this doc covers the one-time work before them (and the repeat of it after a
rebuild).

Production runs on one Contabo Cloud VPS (x86_64). The supported path is
Terraform plus cloud-init, with a manual procedure kept as a fallback and as a
reference for what cloud-init does. Placeholders in this doc: `<vps-ip>` is the
server address, `<github-owner>` is the GitHub account or organization that owns
the repository.

## Terraform path

[`infra/terraform/`](../../infra/terraform/) manages:

- the Contabo instance (adopted with `terraform import`, protected by
  `prevent_destroy`), the admin SSH public key stored at Contabo, and the
  cloud-init `user_data` rendered from `cloud-init.yaml.tftpl`;
- three ed25519 key pairs generated by Terraform: the two deploy keys and the
  server's SSH host key (so `known_hosts` can be pinned before the server ever
  boots);
- the proxied Cloudflare DNS records for the app hostnames (`cloudflare.tf`),
  which reference the instance address, so replacing the VPS re-points them;
- the GitHub `production` environment, its five `DEPLOY_SSH_*` secrets, and the
  `NEXT_PUBLIC_*` repository variables (`github.tf`).

`imports.tf` adopts resources that existed before Terraform did. Keep it while
state is local: a fresh clone has no state, and without the import blocks
`terraform plan` would propose creating a second VPS and duplicate DNS records.

### Variables and credentials

Copy `terraform.tfvars.example` to `terraform.tfvars` (gitignored) and fill it
in. `variables.tf` documents each variable: the Cloudflare zone id, the Contabo
instance id and image id, the admin SSH public key, and the `NEXT_PUBLIC_*` map
for the web image. Provider credentials (Contabo, Cloudflare, GitHub) come from
environment variables read by the providers, listed in `providers.tf`; none of
them belongs in a `.tf` file, a plan or git. The GitHub token needs admin on the
repository because managing environments requires it.

### Apply

From `infra/terraform/`:

1. `terraform init` (downloads the pinned providers; `.terraform.lock.hcl` is
   committed on purpose).
2. `terraform plan` and read it. A plan that wants to replace the instance means
   a reinstall (see below).
3. `terraform apply`.

After the first boot finishes, continue with
[Step 7](#step-7-ghcr-package-visibility-one-time-manual-after-the-first-build)
and [Step 8](#step-8-first-sync-env-files-systemd-units) below, then the
[first production cutover](#first-production-cutover-t11). `terraform output`
prints the pinned `known_hosts` line and an SSH command for the admin login.

### Terraform state

State is local to the machine that runs Terraform (`terraform.tfstate`,
gitignored) and there is no remote backend. Treat the state file as a secret:
keep it only on that machine, back it up encrypted, and never commit it or paste
it into an issue or chat. Losing it means re-adopting resources by import, which
is what `imports.tf` is for.

### What triggers a reinstall

Changing the instance's `user_data` (this includes editing
`cloud-init.yaml.tftpl` and rotating the Terraform-generated keys), `image_id`
or SSH keys reinstalls the server and wipes its disk: the database, MinIO
objects and Kuma data on its volumes go with it. Read the plan before applying
and make sure a restore path exists first (see
[operations.md](operations.md#restore)).

### What cloud-init does

Cloud-init runs once, on the first boot after an install. It installs the base
packages, installs the Terraform-generated host key, creates the `deploy` user
with the two restricted keys, writes an sshd drop-in that disables password and
keyboard-interactive logins, links `rrsync` into place, installs Docker, creates
the `/home/deploy/biasmarket` directories, enables the host firewall for SSH and
web traffic only, and adds swap (two app colors briefly run side by side during
a cutover). The file itself is the reference for exact values.

## Manual provisioning (fallback)

The numbered steps are the manual equivalent of what Terraform and cloud-init
do, for another provider or to understand the Terraform path. They were written
for Ubuntu 24.04; the Ubuntu 26.04 / x86_64 differences are noted where they
matter. Run the steps in order; each depends on the one before it. Commands
prefixed `# local:` run on your own machine, not the VPS.

| Step | What it does                         | Done by (Terraform path)                                                                |
| ---- | ------------------------------------ | --------------------------------------------------------------------------------------- |
| 1    | packages, Docker, `deploy` user      | `cloud-init.yaml.tftpl` (`user_data`)                                                   |
| 2    | `rrsync`                             | cloud-init symlink: on Ubuntu 26.04 `rsync` installs `/usr/bin/rrsync` (no `rrsync.gz`) |
| 3    | the two deploy SSH keys              | `tls_private_key` resources in `contabo.tf`                                             |
| 4    | restricted `authorized_keys`         | cloud-init, using the public keys from step 3                                           |
| 5    | pin `known_hosts`                    | the host key is generated by Terraform and injected, so it is known before boot         |
| 6    | GitHub secrets/variables/environment | `github.tf`                                                                             |
| 7    | GHCR package visibility              | manual on every path                                                                    |
| 8    | first sync, env files, systemd units | manual on every path                                                                    |

The `deploy` OS user is a Docker-group member, which is root-equivalent in
practice. It is not a containment boundary; the real security boundary is SSH
key secrecy and CI-runner integrity (see decision 10 of the
[blue/green plan](../../.artifacts/2026/08/20260810--bluegreen-zero-downtime-deploy/plan.md),
kept there as history). The resulting directory layout is in
[deploy.md](deploy.md#runtime-layout).

### Step 1: packages, Docker, the `deploy` user

```bash
sudo apt-get update
sudo apt-get install -y rsync openssh-server curl

# Docker Engine + Compose plugin
curl -fsSL https://get.docker.com | sudo sh
# (see https://docs.docker.com/engine/install/ubuntu/ for the manual/apt-repo
# alternative if you'd rather not pipe a script to sh)

sudo useradd --create-home --shell /bin/bash deploy
sudo usermod -aG docker deploy
newgrp docker   # only needed in your own shell if you're testing as `deploy` interactively

sudo mkdir -p /home/deploy/biasmarket/{env,caddy/active,state,releases}
sudo chown -R deploy:deploy /home/deploy/biasmarket
```

An apt lock held by another `apt-get` process is not fixed by deleting the lock
file. Wait for the package operation to finish and retry if needed.

### Step 2: install `rrsync`

> Ubuntu 26.04: the `rsync` package already installs `/usr/bin/rrsync` and there
> is no `rrsync.gz`. Skip the `gunzip` below and run
> `sudo ln -sf /usr/bin/rrsync /usr/local/bin/rrsync` so the `authorized_keys`
> lines keep working unchanged. The gunzip form applies to Ubuntu 24.04.

Ubuntu's `rsync` package ships `rrsync` gzipped, not on `PATH`. Unpack it once
([Ubuntu manpage](https://manpages.ubuntu.com/manpages/noble/man1/rrsync.1.html)):

```bash
sudo sh -c 'gunzip -c /usr/share/doc/rsync/scripts/rrsync.gz > /usr/local/bin/rrsync'
sudo chmod 755 /usr/local/bin/rrsync
rrsync --help   # confirm it runs
```

### Step 3: generate the two deploy SSH keys

Both ed25519, both **without a passphrase** (used non-interactively by CI).
Generate them somewhere you control; your own machine is fine, they never need
to leave it except as pasted GitHub secrets:

```bash
# local:
ssh-keygen -t ed25519 -N "" -C "biasmarket-deploy-key-a-rsync" -f biasmarket_key_a
ssh-keygen -t ed25519 -N "" -C "biasmarket-deploy-key-b-dispatch" -f biasmarket_key_b
```

This produces `biasmarket_key_a[.pub]` and `biasmarket_key_b[.pub]`. The two
**private** key files' contents go into GitHub secrets (Step 6). The two
**public** key files go into the VPS's `authorized_keys` (next step).

The private and public key of a pair must match. If a key is regenerated,
replace both its public line in `authorized_keys` and its GitHub secret. Never
paste private key contents into chat, logs, commits or issue reports; rotate any
key that was exposed.

### Step 4: restrict both keys via `authorized_keys`

A single forced-command key restricted to "run deploy.sh" would silently break
the rsync step (`rrsync` and a `command=` dispatcher cannot be composed on one
key), which is why there are two. As the `deploy` user on the VPS:

```bash
sudo -iu deploy
mkdir -p ~/.ssh && chmod 700 ~/.ssh
```

Append two lines to `~/.ssh/authorized_keys`, pasting each `.pub` file's content
after the `command=...` prefix (see
[sshd's `AUTHORIZED_KEYS FILE FORMAT`](https://man.openbsd.org/sshd#AUTHORIZED_KEYS_FILE_FORMAT)
for what the options mean). The exact lines are the ones in
`cloud-init.yaml.tftpl`:

```
command="/usr/local/bin/rrsync /home/deploy/biasmarket/",no-port-forwarding,no-X11-forwarding,no-agent-forwarding,no-pty ssh-ed25519 <key-a-public-key> biasmarket-deploy-key-a-rsync
command="/home/deploy/biasmarket/bin/ssh-deploy-dispatcher.sh",no-port-forwarding,no-X11-forwarding,no-agent-forwarding,no-pty ssh-ed25519 <key-b-public-key> biasmarket-deploy-key-b-dispatch
```

```bash
chmod 600 ~/.ssh/authorized_keys
exit   # back to your own sudo-capable user
```

Key B's target script (`/home/deploy/biasmarket/bin/ssh-deploy-dispatcher.sh`)
does not exist yet: it arrives via key A's first rsync (`cd.yml`'s
`sync-and-deploy` job, or a manual first sync, see Step 8). Make it executable
once it lands:
`sudo -u deploy chmod +x /home/deploy/biasmarket/bin/ssh-deploy-dispatcher.sh`.
The dispatcher script documents its exact allowlist in its header comment: it
never `eval`s `$SSH_ORIGINAL_COMMAND`, only matches it against anchored regexes
for the handful of literal shapes `cd.yml` sends.

Because key A is forced through `rrsync` rooted at the deploy directory, the
rsync destination must be relative: `deploy@<vps-ip>:.`. Passing the absolute
path makes `rrsync` resolve it a second time under its root and fail. The CD
workflow uses `:.` for the same reason.

### Step 5: pin `known_hosts`

Capture the host key once, **verified out-of-band through your provider's
console** (Contabo: the VNC console in the customer panel). This is not needed
on the Terraform path, where the host key is generated by Terraform and known in
advance. Blind trust of the first `ssh-keyscan` is exactly what host-key pinning
exists to avoid, since an attacker in a position to intercept the very first
connection could substitute a key:

```bash
# local:
ssh-keyscan -t ed25519 <vps-ip> > known_hosts_candidate
cat known_hosts_candidate
```

Then, separately, open the provider console, log in, run
`ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`, and confirm the fingerprint
matches `known_hosts_candidate` before trusting it. The verified file's contents
become the `DEPLOY_SSH_KNOWN_HOSTS` GitHub secret (Step 6).

### Step 6: GitHub secrets, variables, the `production` environment

Create the environment first: Settings, Environments, New environment, named
`production`
([GitHub docs](https://docs.github.com/en/actions/how-tos/manage-environments/create-environment)).
`cd.yml`'s `sync-and-deploy` job and `cleanup-fallback.yml`'s job both declare
`environment: production`, which is what makes environment-scoped secrets the
right place (and gives an optional required-reviewers approval gate for free).

Inside that environment (Settings, Environments, `production`, add secret;
[secrets docs](https://docs.github.com/en/actions/security-guides/using-secrets-in-github-actions)):

| Name                      | Value                                        |
| ------------------------- | -------------------------------------------- |
| `DEPLOY_SSH_HOST`         | VPS hostname or IP                           |
| `DEPLOY_SSH_USER`         | the deploy OS user                           |
| `DEPLOY_SSH_KNOWN_HOSTS`  | Contents of the verified file from Step 5    |
| `DEPLOY_SSH_KEY_RSYNC`    | Contents of `biasmarket_key_a` (private key) |
| `DEPLOY_SSH_KEY_DISPATCH` | Contents of `biasmarket_key_b` (private key) |

The `NEXT_PUBLIC_*` values are not secrets and are not environment-scoped. They
are repository-level **variables** (Settings, Secrets and variables, Actions,
**Variables** tab), baked into the `web` image as build args by `cd.yml` and
already public in every browser bundle
([variables docs](https://docs.github.com/en/actions/learn-github-actions/variables)).
The list and what each one is for is in
[deploy.md](deploy.md#variables-and-secrets); set them before the first `cd.yml`
run that builds `web`.

### Step 7: GHCR package visibility (one-time, manual, after the first build)

`cd.yml`'s `build-push` job has to run once (any push to `main`) before the
packages exist. After that first successful run creates the three packages
(`biasmarket-api`, `biasmarket-web`, `biasmarket-workers`), set each to
**public** visibility. It does **not** inherit from the repository being public
([GitHub docs](https://docs.github.com/en/packages/learn-github-packages/configuring-a-packages-access-control-and-visibility)):

1. `https://github.com/orgs/<github-owner>/packages` (or
   `https://github.com/<github-owner>?tab=packages` for a user account) and open
   each of the three packages.
2. Package settings (right sidebar), Danger Zone, Change visibility, Public.

This is what lets the VPS pull images with no registry credentials. Keeping them
private would need a `docker login` step with a token added on the VPS; that is
not the default path and is not implemented.

### Step 8: first sync, env files, systemd units

With keys and secrets in place, either push to `main` (lets `cd.yml` do the
first rsync) or sync once by hand. If you sync by hand, do it from Linux or a
container, not macOS: `/usr/bin/rsync` on macOS is Apple's openrsync, which the
Python `rrsync` on Ubuntu 26.04 rejects
(`invalid rsync-command syntax or
options`). For example, run the command below
inside an `ubuntu:24.04` container with `rsync` and `openssh-client` installed
and the repo's `infra/vps` bind-mounted read-only.

```bash
# local, using key A directly (bypasses CI for a one-time manual bootstrap):
rsync -az \
  --exclude 'env/*.env' \
  --exclude 'state/' \
  --exclude 'caddy/active/*.caddy' \
  --exclude 'releases/' \
  -e "ssh -i biasmarket_key_a -o StrictHostKeyChecking=yes" \
  infra/vps/ deploy@<vps-ip>:.
```

On a never-deployed server the first `cd.yml` run does this sync itself: its
staleness guard queries the VPS with the dispatch key before the dispatcher
script has been delivered, and treats ssh exit `127` (script not installed yet)
as "first deploy, skip the ancestry check". A connection failure (exit `255`) or
any other error still fails the job. That first CD run still ends red at the
last step (`deploy.sh` refuses with "never been bootstrapped"), by design:
`--bootstrap` is manual only. Run `--bootstrap` yourself afterwards.

Then, on the VPS as `deploy` (`sudo -iu deploy`, from
`/home/deploy/biasmarket`):

```bash
chmod +x bin/ssh-deploy-dispatcher.sh bin/migration-watchdog.sh deploy.sh

# populate real env files; see each .example's header comment for what goes in
# it. These are production secrets and must be provisioned securely; they are
# never committed or synced by CD.
cp env/shared.env.example env/shared.env       # then edit
cp env/blue.runtime.env.example env/blue.runtime.env
cp env/green.runtime.env.example env/green.runtime.env
cp env/watchdog.env.example env/watchdog.env   # KUMA_MIGRATION_PUSH_URL comes after Kuma is up
```

`env/shared.env`, `env/blue.runtime.env`, `env/green.runtime.env` and
`env/watchdog.env` are deliberately excluded from rsync and must exist on the
VPS before bootstrap, created from the reviewed production secret values. Which
variable groups matter is summarized in
[deploy.md](deploy.md#configuration-files).

Install the migration-watchdog systemd units:

```bash
sudo cp /home/deploy/biasmarket/systemd/biasmarket-migration-watchdog.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now biasmarket-migration-watchdog.timer
sudo systemctl status biasmarket-migration-watchdog.timer   # should show "active (waiting)"
```

This timer is deliberately **not** part of `deploy.sh`: a wedged deploy must not
be able to silence its own stuck-migration alarm. If it later fails silently,
check with
`sudo journalctl -u biasmarket-migration-watchdog.service --since "10 min ago"`.

`uptime-kuma` only comes up as part of the
[first production cutover](#first-production-cutover-t11) below
(`deploy.sh
--bootstrap` starts it alongside the other always-on services), so
the monitor setup script cannot run until the cutover has completed. The
procedure is in [operations.md](operations.md#uptime-kuma).

## First production cutover (T11)

Manual, supervised, during a low-traffic window. It is the one deliberate
exception to "no maintenance windows needed" in the blue/green design, since it
is also the first real end-to-end validation of the mechanism against production
data.

Gate on all of the following (provisioning Steps 1-8 above, in order):

- [ ] `env/shared.env` populated with the reviewed production secrets. See
      `infra/vps/env/shared.env.example`'s header comment; never generate or
      commit production secrets from a local dev env file.
- [ ] `infra/vps/docker-compose.yml`'s first line is `name: biasmarket` (verify
      you have not accidentally edited this).
- [ ] Two SSH keys provisioned, `known_hosts` pinned, GitHub secrets and
      variables set (Steps 3-6).
- [ ] GHCR packages public, or a documented alternative in place (Step 7; this
      needs at least one `cd.yml` run first, so it is normally done right after
      the first `main` push post-setup, before this cutover).
- [ ] DNS points at the new VPS, so Caddy can complete ACME issuance as soon as
      it starts. On the Terraform path the DNS records follow the instance
      address (`cloudflare.tf`).

Then, on the VPS as the `deploy` user, from `/home/deploy/biasmarket` (already
synced by an initial manual rsync or a first `cd.yml` run; `--bootstrap` only
works once, before `state/current_color` exists). Use a single login-shell
command rather than typing into an interactive `sudo -iu deploy`, which is easy
to run in the wrong shell or directory:

```bash
sudo -iu deploy bash -lc 'cd /home/deploy/biasmarket && ./deploy.sh --bootstrap <current main HEAD sha>'
```

Immediately after `--bootstrap` succeeds, run the Kuma setup from
[operations.md](operations.md#uptime-kuma): it is the earliest point it can run,
since `uptime-kuma` only just came up.

Verify:

```bash
docker volume ls | grep '^local\s*biasmarket_'   # production volumes
curl -I https://biasmarket.com                    # 200
curl https://api.biasmarket.com/api/health        # {"status":"ok",...}
```

### Bootstrap lessons and operational deviations

The first production bootstrap exposed a few details worth keeping explicit:

- The forced rsync key confines rsync to the deploy directory, so the
  destination must be relative (`deploy@<vps-ip>:.`); see Step 4.
- Run operator commands as a single login-shell command (see the bootstrap
  command above).
- A first deploy on a never-deployed server needs the staleness-guard exemption
  and ends red by design; see Step 8.
- Sync by hand from Linux or a container, never macOS; see Step 8.
- MinIO no longer publishes images on Docker Hub, and `quay.io/minio/*` returns
  401 for anonymous pulls. Compose pins a digest-pinned GHCR rebuild of the last
  open-source release (the same reference as `scripts/ci/e2e-images.sh`) for
  both the `minio` server and `minio-init` (`mc` is in that image). A stale
  `minio/minio` or Quay tag fails bootstrap on a fresh machine.
- Point DNS at the new VPS before `--bootstrap`, so Caddy can complete ACME
  issuance as soon as it starts.
- The private and public key of a deploy key pair must match; rotate both sides
  together and rotate any key that was exposed (Step 3).
- The four `env/*.env` files are intentionally absent from rsync and must be
  created on the VPS before bootstrap (Step 8).
- An apt lock held by another process is waited out, not deleted (Step 1).
- A `Found orphan containers` warning means an unexpected Compose project is
  present. Stop and investigate it; do not use `--remove-orphans` blindly.

There is no supported legacy production stack. If blue/green rollback is not
enough, recover manually using the same `infra/vps/docker-compose.yml`,
`infra/vps/Caddyfile` and `deploy.sh` files used by CD. Never start a second
Compose project against the production volumes: the project name is pinned by
the first line of the compose file, and a different name silently creates new
empty volumes instead of attaching to the production ones.
