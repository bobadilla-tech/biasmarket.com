## 0. Read This First — The One Thing Everyone Should Know

**The core docs (`architecture.md`, `security-payments.md`, `product.md`)
describe a product the code has already grown past.** Specifically:

- The docs describe a single `Order.status` field. The actual schema has had
  three independent fields — `paymentStatus`, `fulfillmentStatus`, `status`
  (cancellation) — since migration `20260720175558`. This is one of the docs'
  own headline recommendations ("split status into three state machines"), and
  it's already done. Good news, but the doc should say so instead of still
  presenting it as a future improvement.
- The docs describe the buyer **uploading payment proof inside the app**
  (`PaymentProof` model, buyer-facing upload endpoint). That never got built.
  What actually shipped: checkout hands the buyer off to **WhatsApp**, and the
  **seller** manually records what was paid (`OrderPayment`, with an optional
  image seller-side) based on that conversation. `PaymentProof` exists in the
  schema and is never written to anywhere in `apps/api/src`. This is not a bug —
  it's a deliberate, documented MVP simplification (`order-status.vo.ts:10-13`)
  — but it means the product's actual payment-proof workflow is materially
  different from what `security-payments.md` §9 and `product.md` §5.6 describe,
  and no one reading only those two docs would know that.
- `docs/core/admin.md` says the Users admin page is "a disabled 'coming soon'
  placeholder." It isn't — `admin-users-table.tsx` and `use-toggle-user-ban.ts`
  are real and wired.

None of this is alarming — it's the normal residue of a team that ships fast and
updates docs slower. But it means **this audit trusts the code over the docs
everywhere they disagree**, and flags every such disagreement explicitly (Rule
1). Fixing the docs is Phase 0 work, not busywork — the gap above (WhatsApp
handoff vs. in-app proof) is exactly the kind of thing that would send a new
engineer down the wrong path.

## 1–2. What BiasMarket Is Today, and the Core Problem

BiasMarket is a **multi-store commerce manager for informal sellers**, K-pop
group-order/import sellers first. One `User` (seller) can own multiple `Store`s.
Each store gets a themed storefront at `/store/:slug`, a product catalog,
configurable payment methods (Yape/Plin/bank transfer/cash) and delivery methods
(pickup/courier), and an order-review dashboard.

The hypothesis in the prompt — "the problem isn't that sellers need another
e-commerce platform, it's that their workflow is fragmented" — matches what's
actually built. The product is not trying to replace Instagram/WhatsApp; it
structures the order/payment/fulfillment bookkeeping around them.
`docs/business/icp.md` confirms the target buyer persona precisely: K-pop "Group
Order Managers" (GOMs) running 30–100+ orders per drop through Google Forms +
Sheets + DM screenshots today.

The actual flow shipped is:

```
Buyer browses store → adds to cart → checkout (delivery + payment method) →
Order created (PENDING_PAYMENT) → buyer redirected to WhatsApp to pay →
Seller manually records the payment in the dashboard (OrderPayment) →
Seller approves → VERIFIED → ORDERING → IN_TRANSIT → READY → COMPLETED
```

This is a real, working, tenant-isolated version of the "chaos killer" loop —
with one structural gap: **the buyer's part of the loop ends outside the app**
(WhatsApp), and the confirmation screen they land on is minimal (order ID +
"check your email," no summary). The seller's part of the loop is the most
polished surface in the whole product (see §3, §7).

## 4. Buyer Identity — Global Account Across Stores?

**Does not exist today, and the current data model is built the opposite way on
purpose.**

- `Customer.storeId` + `@@unique([storeId, phone])` — a phone number is unique
  **per store**, not globally. Two different stores can have two entirely
  separate `Customer` rows for the same phone number, with independent passwords
  and independent verification state.
- Session cookies are signed HMAC tokens carrying `{customerId, storeId}`, and
  every buyer-facing query (`assertStoreMatch`, `getProfile`) explicitly filters
  by that `storeId`. A Store A session cannot read Store B's data — this is
  correctly enforced, not accidentally missing.
- No `Address` model — delivery info is inlined per-order as JSON
  (`Order.deliveryDetails`).
- No `GlobalCustomer`/`PlatformUser`/`BuyerAccount` table anywhere (confirmed by
  repo-wide grep).

**What it would take to build the vision in the prompt**
(`biasmarket.com/account` aggregating orders across stores): a new
platform-level identity table separate from `Customer`, a session redesign no
longer scoped to one `storeId`, and a migration path for existing per-store
`Customer` rows (do you merge same-phone rows across stores automatically?
that's a real product decision, not just an engineering one — a phone number
reused across two stores today is _coincidentally_ the same person or
_coincidentally_ not, and the system has no way to know which).

This is real, non-trivial work — not a "add a nullable column" fix.
**Recommendation: don't build it now.** Nothing in the current single-store
buyer flow blocks it later (the per-store `Customer` model can become "the
merchant-facing account for one store" underneath a future global identity,
similar to how Shopify separates a buyer's platform identity from a store's
customer record). Revisit only once there's a second or third store with
overlapping buyers in practice — right now, with the ICP being sellers acquired
one at a time via cold DM (`docs/business/gtm.md`), it's very unlikely a real
buyer has ordered from two BiasMarket stores yet.

## 5. Multi-Tenant Architecture

**This is the strongest part of the codebase.** A dedicated authorization audit
across all 13 tenant-scoped modules (`products`, `categories`, `collections`,
`store-sections`, `payment-config`, `delivery-config`, `pickup-points`,
`notifications`, `stats`, `orders`, `customers`, `stores`, `customer-auth`)
found **zero IDOR gaps** — every mutation and every single-resource read goes
through an `assertOwnership`/`findOwned*`/`findRowByIdForStore` helper that
re-verifies `storeId` ownership after fetching by id. This is the flat
"per-service ownership check" design CLAUDE.md describes, and unlike a lot of
codebases that claim this pattern, it's actually followed everywhere,
consistently. One historical gap was found and already fixed:
`store-sections.service.ts`'s `reorder()` had a TOCTOU pattern
(preflight-checked ownership, then wrote unscoped) — caught in a Codacy-review
cleanup pass (2026-08-08) and fixed with a scoped `updateMany` + count
assertion. The same pattern is flagged but _not yet fixed_ in
`collections.service.ts`'s `reorderProducts` — see §13.

There is **no** global `TenantMiddleware`/`AsyncLocalStorage` layer —
`architecture.md`'s design for one is aspirational and undeployed. It isn't
needed today because the per-service pattern above covers the same ground
correctly, but it does mean tenant-safety is enforced by convention (every new
service method must remember to call the helper) rather than by a structural
guarantee that's impossible to bypass. This is an acceptable tradeoff at current
team size, worth revisiting only if the team grows or a service method ever
ships without review.

**Path-based routing (`/store/:slug`) is the right call to keep at MVP**, and
nothing in the codebase makes a later move to subdomains painful: slug is
already the tenant key everywhere (DB, API routes, frontend routes), and nothing
hardcodes single-domain assumptions deep in the stack. The main real blocker for
subdomains later is infrastructure (wildcard TLS, wildcard DNS, SSR host-based
routing in Next.js), not the current architecture — this matches
`architecture.md`'s own "no subdomains until justified" call, and the codebase
gives no reason to second-guess it.

## 6. Orders and the Order State Machine

This is genuinely well-built. `order-status.vo.ts` defines the transition tables
and `assertPaymentTransition()` actually enforces them (not just documentation)
— confirmed by dedicated unit tests (`order-status.vo.spec.ts`,
`order.entity.spec.ts`).

- **PaymentStatus**:
  `PENDING_PAYMENT → {PARTIALLY_PAID, PAYMENT_SUBMITTED, VERIFIED, REJECTED, CANCELLED}`;
  `PARTIALLY_PAID →` same five;
  `PAYMENT_SUBMITTED → {PARTIALLY_PAID, VERIFIED, REJECTED}`;
  `VERIFIED`/`REJECTED`/`CANCELLED` are terminal.
- **FulfillmentStatus**: strictly linear
  `ORDERING → IN_TRANSIT → READY → COMPLETED`, no skipping, and hard-gated on
  `paymentStatus === VERIFIED` before any fulfillment transition is allowed at
  all (`order.entity.ts:39-47`).
- **Payment status and fulfillment status are correctly decoupled** — exactly
  what the prompt asked to check for. `OrderStatus` (ACTIVE/CANCELLED) is a
  third, independent axis for cancellation. This is the three-way split
  `architecture.md` recommends, already implemented.
- **Who can transition what**: every mutating endpoint requires `AuthGuard` +
  `assertOwnership(storeId, userId)` before the transition runs. No public
  endpoint can mutate order status.
- **Auditability**: `AuditLog` rows are written on payment approve/reject
  (`review-payment.usecase.ts:143-154`) and on cancellation
  (`cancel-order.usecase.ts:135-151`) — but **not** on fulfillment advances or
  on `addPayment`. Minor gap, low blast radius (these aren't the disputed
  actions a seller would need to prove later).
- **Cancellation/refund**: fully modeled as bookkeeping — `RETAINED` (full or
  partial), `REFUNDED`, `STORE_CREDIT` resolutions, with
  `retainedAmount`/`releasedAmount` tracked and stock released. There's no
  actual money movement (correct — no payment gateway exists yet), it's a record
  of what the seller decided to do, which is the right level of abstraction for
  a manual-payment system.
- **Two real correctness bugs were found and fixed by the team already**, worth
  calling out because they show the state machine had genuine sharp edges that
  are now closed:
  1. **Approval without payment** (fixed 2026-08-06): nothing stopped a seller
     from approving an order (`→ VERIFIED`, triggering stock decrement) with
     `paidAmount === 0`. Confirmed as a live bug, not theoretical — 5 seed
     fixtures had shipped in exactly this broken state. Fixed with a guard in
     `ReviewPaymentUseCase`.
  2. **Payment precision bug** (fixed 2026-08-06): `paidAmount`/`pendingAmount`
     were computed with plain JS `Number` arithmetic on `Decimal` fields,
     producing values like `pendingAmount: 59.989999999999995`. This wasn't
     cosmetic — the overpayment guard compared against that broken value, so a
     seller entering the _exact_ amount owed could get rejected. The same buggy
     pattern was independently copy-pasted into three different services; fixed
     once with a shared `Prisma.Decimal`-space helper
     (`common/payment-summary.ts`) used everywhere now.

**One unresolved correctness risk, not yet caught by the team**: the stock-hold
check in `create-order.usecase.ts:243-253` (read `variant.reserved`, compare to
requested quantity, then write) has **no row lock**, unlike the `PickupPoint`
availability check a few lines later in the same file which explicitly uses
`FOR UPDATE`. Under concurrent checkout requests for the same limited-stock
variant, two buyers can both pass the availability check before either write
commits — real overselling risk on exactly the "limited drop" scenario the
product is built for. This is the single most important engineering fix in this
whole audit (see §12, §16 #1).

## 7. Payment Proof System

**The proof-of-payment system as described in `security-payments.md` doesn't
exist. What exists instead is a seller-recorded payment-with-optional-image
system, and it's solid but has real gaps.**

- `PaymentProof` (buyer-uploaded, `PENDING_REVIEW`/`APPROVED`/`REJECTED`) is
  schema-only — never created anywhere in `apps/api/src`.
- What's actually used: `OrderPayment`, created by the **seller** via
  `POST stores/:storeId/orders/:orderId/payments`, guarded by `AuthGuard` +
  `assertOwnership`. No buyer-facing upload path at all.
- **File validation is real but partial**: max 5MB, and actual magic-byte checks
  (not trusting `Content-Type`) — PNG signature check is solid (8-byte match),
  JPEG check is weak (only the 2-byte SOI marker, easy to satisfy with a crafted
  non-image file). No EXIF stripping, no re-encoding — files are stored raw.
- **Access control on the images themselves is the real gap**: uploaded files
  get a permanent public URL (`${S3_PUBLIC_URL}/${bucket}/${key}`) with no
  signing and no ownership check on read. Anyone who obtains the URL (via UUID
  guess, log leakage, browser history, a shared screenshot) can view a
  customer's payment screenshot — which may contain a bank account number or
  payment app QR — indefinitely, with no expiry and no audit trail on who viewed
  it. This is more sensitive than a product image and is currently protected by
  the same "public bucket, unguessable UUID" model as product photos.
- **Rejection is terminal** — no re-open/resubmit path exists once an order is
  `REJECTED`.
- **No rate limiting** on the payment-registration endpoint at all (contrast:
  `/contact` and `/restock` are throttled, this isn't) — low risk today since
  it's seller-authenticated, not public, but worth noting given it's a
  file-upload endpoint.
- `StorageService` does validate its own required env vars eagerly at boot
  (`requiredEnv()` throwing on missing `S3_BUCKET`/`S3_PUBLIC_URL`/etc.) — this
  is a good pattern that should be the template for the "no startup env-var
  validation" gap noted in `deploy.md`'s known limitations (§12).

**Minimum robust model recommendation** (not "build now," just "what good looks
like" per the prompt's ask): keep the seller-recorded model — it fits the
WhatsApp-handoff reality — but (a) serve proof/payment images through an
authenticated, ownership-checked endpoint instead of a public bucket URL, and
(b) decide deliberately whether `PaymentProof` should be deleted from the schema
or actually wired up for a future buyer-upload flow. Living dead code in the
schema is a minor but real source of confusion (an engineer reading the schema
today would reasonably assume proof upload is a buyer-facing feature).

## 8. Future Payment Gateways (Culqi, etc.) — Foundations, Not Implementation

**Correctly not built, and the current abstractions are close to what you'd want
later without having overbuilt for it.**

What's already in a good shape for future automated payments:

- `PaymentMethodType` enum and `PaymentMethodConfig` per store already separate
  "which payment methods this store accepts" from hardcoded logic — adding a
  `CULQI`/`STRIPE` variant later is additive, not a rewrite.
- `OrderPayment` already models "a payment record with
  amount/method/note/image," which is most of what a `PaymentAttempt`
  abstraction needs — a gateway integration would add a
  `providerReference`/`providerStatus` pair to this model rather than needing a
  new one.
- The `paymentStatus` state machine already has the right shape
  (`PENDING_PAYMENT → PAYMENT_SUBMITTED/PARTIALLY_PAID → VERIFIED/REJECTED`) —
  an automated gateway would just add a new _trigger_ for the same transitions
  (a webhook calling `ReviewPaymentUseCase`-equivalent logic instead of a seller
  click), not new states.

What's genuinely missing and **should not be built until there's a concrete
gateway integration to build against**:

- No `PaymentProvider`/`PaymentReference` concept, no webhook infrastructure at
  all (confirmed zero webhook code anywhere in the repo), no idempotency-key
  handling, no reconciliation job.
- No `paidAmount` currently gets adjusted for gateway fees — irrelevant now,
  would matter the moment real money moves through the platform.

**Legal/regulatory note (per the prompt's Rule 7):** whether BiasMarket would
need to register as a payment facilitator, hold funds, or handle KYC to
integrate a gateway like Culqi, and what obligations apply to storing even a
screenshot of someone's bank transfer, are Peru-specific legal/compliance
questions this audit is not qualified to answer and does not attempt to. Get
that guidance before scoping Phase 5 seriously, not after building it.

## 9. Monetization Analysis

**No monetization thinking exists in the codebase or docs yet — not
"deprioritized," genuinely not started.** `docs/business/` (8 files) is entirely
GTM/ICP/outreach content — cold-DM scripts, lead-sourcing playbooks, funnel math
for _user acquisition_. The one pricing-adjacent line found is the outreach
script's answer to "is it free?": _"yeah for now I'm setting it up for early
users for free."_ No pricing tiers, no fee model, no revenue projection
anywhere.

Given the ICP (K-pop GOMs, high order volume per drop, currently paying nothing
for Google Forms + Sheets), here's how the five models stack up against what the
code and docs reveal about actual seller behavior:

- **Model A (SaaS/monthly)**: Lowest friction to _build_ (a plan field on
  `Store`), highest friction to _sell_ — GOMs are often not registered
  businesses, monthly recurring cost is a real psychological barrier for someone
  running this as a side activity, and there's currently zero telemetry to know
  what "value delivered" would justify a price point.
- **Model B (transaction fee / % of GMV)**: Aligns incentive with the platform
  (BiasMarket only earns when the seller earns) and is the most natural fit
  given the platform never touches the money today — but with no payment
  gateway, there's no clean collection mechanism (you'd have to invoice/manually
  collect the fee, which reintroduces the exact "chaos" the product exists to
  remove).
- **Model C (hybrid)**: Same collection problem as B until a gateway exists;
  premature to design before B or A is validated.
- **Model D (payments monetization)**: Explicitly the prompt's "future, not MVP"
  bucket — correctly out of scope now (§8).
- **Model E (freemium)**: Best-fitting model _today_ given the acquisition
  motion already built (`gtm.md`'s free-for-early-users pitch is already a soft
  freemium framing) — ship free, learn what feature a seller would actually pay
  to unlock (multi-store? analytics? removing a "Powered by BiasMarket" mark?
  faster payout reconciliation once B exists?).

**What to measure before deciding** (this is the actual deliverable of this
section): activation rate (store created → first `VERIFIED` order),
orders-per-store-per-month once real sellers are on it, GMV per store, seller
retention at 30/60/90 days, and — the single most informative number — whether a
seller, given the choice, keeps using the in-app order/payment tracking or
reverts to their spreadsheet after week 2. None of that data exists yet because
there's no production seller yet (`docs/business/gtm.md`'s targets are 5–10
activated stores/week, i.e., outreach is just starting). **Recommendation: do
not choose a monetization model until you have this data from real sellers —
freemium/free-for-now is the correct default while collecting it, exactly as
`gtm.md` already assumes.**

## 13. Security Review

No exaggerated findings — only what the code supports.

**Confirmed strong:**

- **Zero IDOR found** across all 13 tenant-scoped modules — every mutation and
  by-id read is ownership-checked
  (`assertOwnership`/`findOwned*`/`findRowByIdForStore`), confirmed by direct
  code audit, not assumption.
- **Buyer session isolation is correct** — HMAC token embeds
  `{customerId, storeId}`, every query filters by both, cross-store replay is
  blocked by `assertStoreMatch`.
- **Global deny-by-default auth guard** (`@thallesp/nestjs-better-auth`) — every
  route requires authentication unless explicitly `@Public()`.
- **CORS locked to `WEB_URL`**, global
  `ValidationPipe({whitelist, forbidNonWhitelisted})` blocks
  parameter-pollution-style field injection (e.g., a client can't smuggle an
  extra `ownerId` into a DTO).
- **Public storefront reads correctly scoped** — DRAFT/deleted/discontinued
  products, and other stores' data, are never leaked through public endpoints;
  confirmed by direct query inspection, not just endpoint naming.

**Real, actionable findings (status re-checked at update time):**

1. ✅ **FIXED same-day** (residual: pre-fix uploads still exposed — see Update).
   **Payment-proof/payment images are unauthenticated, permanently public URLs**
   (§7, §12). Attack: anyone who obtains a URL (link sharing, browser history
   sync, a support screenshot, log line) can view a buyer's bank-transfer
   screenshot indefinitely. Fix: proxy image reads through an authenticated
   endpoint that re-checks store ownership, same pattern already used for every
   other tenant-scoped resource in this codebase.
2. ✅ **FIXED same-day** (helmet shipped; global CSRF guard deferred by design —
   see Update). **No app-wide CSRF protection or `helmet`** — acknowledged in
   `deploy.md` as a known limitation. Buyer-auth mutation routes have an
   `Origin`/`Referer` check (a reasonable minimal bar given cookie-based auth),
   but nothing else does.
3. **Re-checked directly, not a current gap** —
   `apps/web/app/[locale]/(dashboard)/admin/layout.tsx:21-32` already
   redirects non-admins before rendering the sidebar (`isAdmin`/`impersonatedBy`
   gate). No plan claims to have fixed this specifically, so treat this original
   finding as stale at write-time rather than fixed since. **`/admin` route has
   no client-side auth guard on the page shell** — a logged-in non-admin can
   load the `/admin` page and see the sidebar UI (nav labels, layout) even
   though every actual API call underneath 403s.
4. ✅ **FIXED same-day. No general rate limiting** on state-changing endpoints
   outside auth/contact/restock — a compromised or careless seller session could
   hammer payment-registration or order-mutation endpoints with no backpressure.
5. **STILL OPEN — not addressed by any same-day fix. Weak file-signature check
   for JPEG** (2-byte SOI marker only) on the payment-registration upload — low
   severity, authenticated-only endpoint, but worth tightening next time that
   upload path is touched.

No SQL injection surface found (Prisma parameterized queries throughout), no
mass-assignment risk found (whitelist validation pipe), no session-fixation
pattern found, no webhook surface exists to secure (none built).

## 14. Recommended Architecture

**The existing modular monolith is the right architecture — do not propose
microservices, do not propose a rewrite.** What the audit actually recommends is
_closing gaps in the current design_, not replacing it:

```
Global Buyer Identity        → Deliberately NOT built yet. Correct call. Current per-store
                                Customer model is a valid foundation to build under later.
Seller / Store Tenancy       → Solid. Per-service ownership checks, zero IDOR found.
                                Keep this pattern; don't add tenant middleware speculatively.
Products                     → Solid, complete.
Orders                       → Solid, 3-axis state machine already matches the "ideal model"
                                the audit would have otherwise recommended. Close the stock-
                                hold race condition (§6, §16) — that's the one structural fix.
Manual Payment Proof         → Working seller-recorded model, needs authenticated image
                                serving. Decide the fate of the unused PaymentProof model.
Order State Machine          → Already correct; keep AuditLog coverage consistent
                                (fulfillment advances + addPayment currently uncovered).
Future Payment Abstraction   → PaymentMethodType/PaymentMethodConfig/OrderPayment already
                                shaped correctly to extend later. Don't add PaymentProvider/
                                webhook/idempotency scaffolding until there's an actual
                                gateway to integrate against.
```

The one structural addition worth considering, and only because it's cheap: a
thin authenticated-file-serving layer in front of the storage bucket (one new
controller endpoint that checks ownership, then streams/redirects to a
short-lived signed URL). This closes finding §13.1 without touching the
order/payment domain logic at all.

  email sends) doesn't need it.
- **Buyer-side in-app proof upload** — only worth building if real sellers
  report WhatsApp handoff as actual friction; untested assumption today, don't

- **AI/ML features of any kind** — explicitly out of scope per
  `docs/plans/2026-07-31-platform-growth-features-plan.md`'s own stated

- **Row-Level Security at the Postgres layer** — `architecture.md` floats this

## 19. Final Executive Summary

**What BiasMarket is today:** a working, multi-tenant store manager for K-pop
group-order sellers — create a store, list products, take orders, record manual
payments, review and approve them, track fulfillment through import/shipping
states, all correctly isolated per store with no found authorization gaps.

**The problem being solved:** replacing the
Google-Forms-plus-Sheets-plus-DM-screenshot chaos that group-order sellers
currently run on, without forcing them off the payment/communication channels
(Yape, bank transfer, WhatsApp) their buyers already trust.

**What's already working:** the seller-side loop end to end — catalog, checkout,
payment recording, approval, fulfillment tracking — plus a genuinely strong
tenant-isolation posture and an order state machine with enforced, tested
transitions. The dashboard is more complete than a typical MVP.

**What's missing (updated same day):** at write-time — a stock-hold concurrency
fix, authenticated payment-proof-image access, rate limiting/CSRF/helmet, error
tracking, and docs describing a payment-proof flow that was never built. **All
five shipped within hours of this audit landing** (see the Update section at the
top). What's actually missing now: working lint, a decision on backfilling
legacy public payment images, and — the real gap — data from real sellers.

**What to build next:** get linting genuinely running (the one Phase-0 item that
didn't ship, and whose deferral reasoning turned out to be untested), decide the
legacy-image backfill deliberately, then shift fully to running the GTM motion
against real sellers and instrumenting the metrics that will answer whether this
product is actually solving the chaos it's built for.

**What to explicitly postpone:** global buyer identity across stores, any
payment gateway integration, subdomain routing, a themes marketplace, and any
monetization implementation. None of these are blocked by the current
architecture — they're blocked by not having the data yet to justify them.

**How manual payments fit the MVP:** they _are_ the MVP's payment system, not a
placeholder for one — the model (seller-recorded `OrderPayment`, approve/reject,
audit trail, cancellation bookkeeping) is solid and shouldn't be treated as
throwaway scaffolding.

**When automated payments make sense:** once there's real GMV to justify the
integration and legal-review cost, and only after getting Peru-specific
compliance guidance — not before.

**What monetization paths exist:** freemium is the right default right now,
exactly as the team's own GTM docs already assume; a transaction-fee model is
the best long-term fit given the platform doesn't touch money today, but has no
clean collection mechanism until a payment gateway exists.

**What the team should align around:** ship the Phase 0 fixes, get the docs
honest again, and get real sellers on the platform through the GTM motion that's
already written — the product is closer to "actually usable" than "needs more
building," and the next real unlock is data from real sellers, not more
features.
